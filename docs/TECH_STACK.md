# TECH_STACK.md — Selected Technology Stack

## 1. Final Selection

| Concern | Selection |
|---|---|
| Framework | Flutter |
| Language | Dart |
| Platform | Android |
| State management | Riverpod |
| Navigation | go_router |
| Local database | SQLite via Drift |
| Simple preferences | shared_preferences |
| Audio | just_audio |
| Localization | Flutter gen_l10n / ARB |
| Date/formatting | intl where needed |
| Academic content | local JSON assets |
| Images | local PNG/WebP |
| Fonts | local Inter or approved local fallback |
| Testing | flutter_test + unit tests + integration_test where needed |

Use versions compatible with the installed stable Flutter SDK. Avoid blindly pinning versions from old examples.

## 2. Why Flutter

Flutter is chosen because the app:
- is mobile-first;
- targets Android;
- needs consistent custom UI;
- is primarily offline;
- uses many local assets;
- needs touch-friendly drag/drop;
- needs SQLite persistence;
- does not need web-code reuse.

The React prototype is a specification, not a code-sharing target.

## 3. Why Not Capacitor/WebView

Capacitor is not selected for final because:
- final quality should be native Flutter behavior;
- touch drag/drop should be stable;
- lifecycle/persistence should be controlled;
- offline asset handling is cleaner;
- customer asked for an APK, not a wrapped website.

Do not package Vercel/local React as final APK.

## 4. Why Riverpod

Selected for:
- testability;
- explicit dependencies;
- async/local repository integration;
- predictable state;
- no BuildContext dependency for business logic.

Use one state-management strategy consistently.

## 5. Why go_router

Provides:
- centralized routes;
- parameterized module paths;
- predictable navigation;
- recovery/redirect logic if needed.

Do not mix routing packages.

## 6. Why Drift

Selected because:
- attempt history is structured;
- schema is typed;
- queries are testable;
- migrations are explicit;
- transaction support is useful;
- latest/best/history are easy to query.

SQLite stays entirely local.

## 7. shared_preferences

Use only for:
- selected locale;
- first-run/splash flags;
- lightweight non-critical preferences.

Do not store full attempt history there.

## 8. Audio

Use `just_audio`.

Requirements:
- bundled assets;
- no streaming URL;
- play/pause;
- progress;
- duration;
- safe stop on track/screen changes.

## 9. Content Format

Preferred:

```text
assets/data/modules/
  module_1.json
  module_2.json
  module_3.json
```

Typed Dart models validate content.

Do not fetch academic JSON remotely.

## 10. Asset Formats

Images:
- optimized WebP where suitable;
- PNG for transparent/logo needs.

Audio:
- current source WAV is acceptable;
- compressed local audio may be evaluated later if size matters and all QA passes.

## 11. Fonts

No runtime Google Fonts.

Bundle Inter if legally/source-file available; otherwise use documented local system fallback.

## 12. Android Tooling

Use stable Android tooling generated by current Flutter.

Do not manually downgrade Gradle/Kotlin/AGP without a verified reason.

Minimum SDK:
- use current Flutter-supported minimum at project creation unless customer/device requirement needs otherwise;
- record actual value in `DECISIONS.md`.

## 13. Prohibited Runtime Technology

Unless scope changes:
- Firebase;
- Supabase;
- REST client for core functions;
- GraphQL;
- authentication SDK;
- analytics SDK;
- remote config;
- Google Fonts HTTP;
- remote media CDN;
- embedded Vercel web app.

## 14. Dependency Policy

Before adding a package:
1. prove why Flutter SDK cannot reasonably solve it;
2. prefer mature focused packages;
3. avoid overlaps;
4. check offline behavior;
5. check Android support;
6. add tests for critical package-dependent behavior;
7. document architecture-impacting changes.

Codex must not add dependencies “just in case”.
